A Content-Security-Policy you can ship from a meta tag

GitHub Pages cannot send headers. A <meta> policy covers most of what you want anyway — including dropping 'unsafe-inline' — as long as you know the three directives it will silently ignore.

25 August 2026 DuoFine Engineering Security 6 min read

A Content-Security-Policy is the one line of defence that turns "someone injected a script" from a breach into a console error. Ours is delivered in the least glamorous way possible: a <meta http-equiv> tag at the top of every page. This note is about what that buys, what it cannot buy, and the small amount of tooling that keeps it honest.

Why a meta tag at all

This site is served by GitHub Pages, which does not let you set response headers. Cloudflare sits in front and can add headers with a transform rule — we use that for Strict-Transport-Security, X-Frame-Options and friends. But a CSP is tightly coupled to the HTML it protects: add a font host, add a script hash, and the policy has to change with the same commit. A header configured in a dashboard drifts. A meta tag lives in the repository, next to the code it describes, and gets reviewed in the same diff.

Two rules for the tag itself: put it before any <script> or <link> in <head>, because it only applies from the point the parser reaches it; and put charset before it, so the policy is parsed in the encoding you think it is.

The three directives a meta CSP ignores

Per the specification, a policy delivered via <meta> drops three things, silently:

  • frame-ancestors — clickjacking protection. Browsers refuse to honour it from a meta tag because the framing decision is made before the document is parsed. Use the X-Frame-Options: DENY header instead; ours comes from Cloudflare.
  • report-uri / report-to — violation reporting. If you want reports, you need a header.
  • sandbox — also header-only.

Everything else — default-src, script-src, style-src, connect-src, img-src, font-src, form-action, base-uri, object-src, upgrade-insecure-requests — works exactly as it would in a header.

The policy, line by line

Here is the policy on this page, wrapped for reading. Hashes are computed at deploy time, which is the last section.

Content-Security-Policy
default-src 'self';
base-uri 'self';
object-src 'none';
frame-src 'none';
script-src 'self' 'sha256-…' 'inline-speculation-rules'
           https://www.googletagmanager.com https://static.cloudflareinsights.com;
style-src 'self';
img-src 'self' data: https://www.googletagmanager.com https://*.google-analytics.com;
font-src 'self';
connect-src 'self' https://formsubmit.co https://cloudflareinsights.com
            https://*.google-analytics.com https://*.analytics.google.com
            https://www.googletagmanager.com;
form-action 'self' https://formsubmit.co;
upgrade-insecure-requests
  • default-src 'self' is the floor: anything not listed comes from this origin or not at all.
  • object-src 'none' and frame-src 'none' because the site embeds nothing.
  • base-uri 'self' stops an injected <base> from redirecting every relative URL.
  • form-action lists the one host the contact form posts to. Without it, an injected form could exfiltrate what people type.
  • font-src 'self' because the fonts are self-hosted — that is its own note.

Getting rid of 'unsafe-inline'

'unsafe-inline' in script-src is the directive that makes a CSP mostly decorative: it allows exactly the injected inline script you were trying to stop. We used to have it, for one reason — a single one-line script at the top of each page:

HTML
<script>document.documentElement.className+=" js"</script>

It adds a class so that reveal animations only hide content when JavaScript is actually running. It has to be inline and it has to be first. The answer is a hash: the SHA-256 of the script's exact text, base64-encoded, listed in script-src as 'sha256-…'. Change one character of the script and the browser refuses to run it — which is the point.

Two other kinds of inline script turned out to need nothing or something else:

  • JSON-LD (type="application/ld+json") is data, not code. The browser never executes it, so CSP does not apply.
  • Speculation rules (type="speculationrules", the JSON that asks Chrome to prerender the next page) are subject to script-src. CSP3 added a dedicated keyword, 'inline-speculation-rules', for exactly this. We list the keyword and the block's hash, so browsers that know either one are covered.

No inline styles, really

style-src 'self' without 'unsafe-inline' means no style="" attributes anywhere in the markup and no <style> blocks. That sounds restrictive until you notice the loophole you actually need: setting styles from JavaScript through the CSSOM (el.style.transform = …, el.style.setProperty('--w', …)) is allowed. Only the attribute in the HTML is blocked.

So the reading-progress bar on this page is driven by style.transform from a scroll handler, the before/after bars on the homepage get their widths from CSS classes that set a custom property, and inline SVG uses presentation attributes (fill, stroke), which CSP does not touch. We removed exactly one style attribute from the whole site and nothing was lost.

Scripts you did not write

The interesting part of a CSP on a real site is the code other people add to your pages:

  • Cloudflare Web Analytics injects <script src="https://static.cloudflareinsights.com/beacon.min.js">. It is an external script from a fixed host, so the host goes in script-src and connect-src.
  • Cloudflare Email Obfuscation rewrites e-mail addresses and injects a decoder from /cdn-cgi/scripts/… on your own origin — covered by 'self'. We turned the feature off for our own addresses anyway (wrap them in <!--email_off--> comments), because it also rewrote the address inside our "message sent" panel into [email protected] until the decoder ran.
  • Rocket Loader, if you enable it, rewrites your script tags and would break under a hash-based policy. We do not use it.
  • Google Analytics is loaded by us, after consent — that note lists the exact allowances.

Keeping it true at deploy time

A hash-based policy has one failure mode: someone edits the inline script and forgets the hash, and the site's JavaScript silently stops. So the hash is never typed by hand. The deploy script walks every HTML file, finds inline scripts that execute, computes their SHA-256 and rewrites the content of the meta tag. A separate check refuses to deploy if any page still contains 'unsafe-inline', a style="" attribute, or an inline script whose hash is missing.

JavaScript · scripts/stamp.mjs (excerpt)
const hashes = inlineScripts
  .filter(s => !s.type || s.type === "speculationrules")
  .map(s => "'sha256-" + createHash("sha256").update(s.body).digest("base64") + "'");

const policy = POLICY.replace("{HASHES}", hashes.join(" "));
The result is a policy that is part of the code review, cannot drift from the HTML it protects, and no longer contains the one keyword that made it optional.
