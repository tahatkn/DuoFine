Self-hosting Poppins: subsets, unicode-range and the missing Turkish letters

The "latin" subset of a Google Font does not contain ş, ğ or İ. What that looks like on a Turkish page, why the browser falls back mid-word, and the six-kilobyte fix.

25 August 2026 DuoFine Engineering Front-end 5 min read

This site is set in Poppins. For a long time it loaded Poppins the easy way — a <link> to fonts.googleapis.com — and then, for the pages that mattered most, the careful way: three .woff2 files in the repository. Both ways were quietly wrong for a site with a Turkish page, and the reason is worth five minutes.

Why self-host at all

Three reasons, in the order they convinced us:

  • Privacy. Loading a font from Google's servers sends the visitor's IP address to Google before they have agreed to anything. In January 2022 a Munich court ruled that doing so without consent violates the GDPR. A privacy policy page that phones Google to render its own headline is a bad look.
  • Speed. A third-party font means a DNS lookup, a TLS handshake and two round trips (the CSS, then the font) to a host that is not yours. Self-hosted fonts ride the connection you already have, and can be preloaded.
  • Control. You decide which weights, which subsets and which font-display behaviour ship — not an API that guesses from the request's Accept-Language and User-Agent.

How Google Fonts actually serves a font

Ask the Google Fonts CSS API for Poppins and you do not get one file per weight. You get several @font-face blocks per weight, one per subset, each with a unicode-range:

CSS · as returned by fonts.googleapis.com (abridged)
/* latin-ext */
@font-face {
  font-family: 'Poppins'; font-weight: 400;
  src: url(…/pxiEyp8kv8JHgFVrJJbecnFHGPezSQ.woff2) format('woff2');
  unicode-range: U+0100-02BA, U+02BD-02C5, …, U+1E00-1E9F, U+1EF2-1EFF, …;
}
/* latin */
@font-face {
  font-family: 'Poppins'; font-weight: 400;
  src: url(…/pxiEyp8kv8JHgFVrJJfecnFHGPc.woff2) format('woff2');
  unicode-range: U+0000-00FF, U+0131, U+0152-0153, …;
}

The browser only downloads a file whose range contains a character the page actually uses. An English page fetches "latin" only. That is the whole reason the subsets exist: the latin file is about 8 KB, the whole font is many times that.

Look closely at the latin range: U+0000-00FF covers ASCII and Latin-1 — ç, ö, ü are in it. U+0131 is the dotless ı, included because it is common in Turkish text that has been through Latin-1 systems. But ş (U+015F), ğ (U+011F), İ (U+0130) and their capitals live in Latin Extended-A, which is in the latin-ext file.

The Turkish page that broke the illusion

When we self-hosted, we copied the three "latin" files and their unicode-range, which is exactly right for an English site. Then we added a Turkish homepage. Here is what the browser does with the word işletme when only the latin face is declared: i renders in Poppins, ş falls outside every declared range and is rendered in the next font in the stack — Arial, on most machines — and letme is back in Poppins. One word, two typefaces, with different x-heights and stroke weights. It is subtle at body size and glaring in a headline.

This is not a bug in the browser; it is unicode-range doing precisely what it says. And it is invisible in every English test you will ever run.

The fix: a second face with its own range

Download the latin-ext file for each weight (they are 5–6 KB each) and declare it as a second @font-face with the same family name and weight, and the latin-ext range:

CSS · site.css
@font-face { font-family: Poppins; font-weight: 400; font-display: swap;
  src: url(/assets/fonts/poppins-400.woff2) format("woff2");
  unicode-range: U+0000-00FF, U+0131, U+0152-0153, U+02BB-02BC, U+02C6, U+02DA, U+02DC,
                 U+2000-206F, U+2074, U+20AC, U+2122, U+2191, U+2193, U+2212, U+2215, U+FEFF, U+FFFD; }

@font-face { font-family: Poppins; font-weight: 400; font-display: swap;
  src: url(/assets/fonts/poppins-400-ext.woff2) format("woff2");
  unicode-range: U+0100-02BA, U+02BD-02C5, U+02C7-02CC, U+02CE-02D7, U+02DD-02FF, U+0304, U+0308,
                 U+0329, U+1D00-1DBF, U+1E00-1E9F, U+1EF2-1EFF, U+2020, U+20A0-20AB, U+20AD-20C0,
                 U+2113, U+2C60-2C7F, U+A720-A7FF; }

English pages still fetch only the latin file; nothing changes for them. The Turkish page fetches both, about 14 KB per weight instead of 8, and every glyph is Poppins. Copy the ranges from Google's CSS rather than typing them — they are the ones the font was actually subset with. (We got this wrong once on the first attempt, by grabbing the file listed after the comment instead of the one it belonged to, and downloaded the Devanagari subset. It was 39 KB and contained no ş either.)

Do not request weights you do not ship

An audit of our stylesheet found font-weight: 500 in four rules, and no 500 file. The CSS font-matching algorithm resolves a missing 500 to 400, so the "medium" intent silently became "regular" everywhere. Two honest options: ship the 500 file, or stop asking for it. We stopped asking; the rules now use 600 where emphasis was meant and 400 where it was not. The lesson generalises: every weight in your CSS should correspond to a file you serve, or you are designing with a typeface that is not there.

A fallback that does not jump

With font-display: swap, text renders immediately in the fallback font and is swapped when Poppins arrives. Poppins is noticeably wider than Arial, so the swap used to reflow every line — a small layout shift on every visit with a cold cache. The modern fix is a metric-compatible fallback: a local face whose size and vertical metrics are adjusted to match Poppins, declared once and placed second in the stack.

CSS · site.css
@font-face {
  font-family: "Poppins Fallback";
  src: local("Arial"), local("Helvetica Neue"), local("Helvetica");
  size-adjust: 113.7%;
  ascent-override: 92.3%;
  descent-override: 30.8%;
  line-gap-override: 8.8%;
}
body { font-family: Poppins, "Poppins Fallback", -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif; }

The percentages come from comparing the two fonts' metrics; tools like fontaine or Next.js's font loader will compute them for you. The effect is that the fallback occupies almost exactly the space Poppins will, so the swap changes the letterforms but not the line breaks. Combined with preloading only the weights used above the fold, the font system costs one connection, three small files, and no layout shift.

Checklist: self-host; copy the subset ranges verbatim; add latin-ext the moment a non-English page exists; ship every weight you reference; give the fallback Poppins's metrics.
