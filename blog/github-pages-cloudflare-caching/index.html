GitHub Pages behind Cloudflare: cache rules, and the purge you cannot skip

Two cache rules, content-hashed asset URLs and one manual step. How the HTML of this site is served from the edge without ever being two hours stale by accident.

25 August 2026 DuoFine Engineering Infrastructure 5 min read

duofine.com is a static site in a public repository. GitHub Pages builds it, Fastly serves it for GitHub, and Cloudflare sits in front of both because the domain's DNS lives there. Three layers of cache for a few HTML files sounds like a lot. Used carefully, it means a visitor in São Paulo or Seoul gets the page from a machine near them, and the origin is barely touched. Used carelessly, it means you push a fix and stare at the old page for two hours.

What GitHub Pages gives you

Every response from Pages carries cache-control: max-age=600 — ten minutes, for HTML and assets alike — and nothing you can configure. There is no _headers file (that is a Netlify and Cloudflare Pages convention; Pages ignores it), no way to set immutable on fingerprinted files, no way to send a security header. Whatever policy you want has to be layered on top.

Two cache rules

In Cloudflare, under Rules → Cache Rules, we have exactly two:

  • assets-immutable — URI path starts with /assets/. Eligible for cache; edge TTL one year; browser TTL one year. Fonts, images and icons live here and never change in place.
  • html-short — URI path ends with .html, or ends with /. Eligible for cache; edge TTL two hours, ignoring the origin's ten minutes (two hours is the lowest option on the free plan); browser TTL respects origin, so a visitor's own browser still re-checks after ten minutes.

The stylesheet and the script are deliberately in neither rule: they sit at the root, not under /assets/, and they are the files that change most often. They get Cloudflare's default treatment, and their URLs carry a version, which is the next section.

Why the asset rule needs content hashes

"Cache for a year" is only safe for a URL whose content can never change. For images that is naturally true — a new image gets a new file name. For site.css and script.js it is not, so their URLs include a version: /site.css?v=…. Originally that was a timestamp, stamped by the deploy script into a hard-coded list of five HTML files. Two problems: a page added later was forgotten, and every deploy busted the cache for both files even when only one had changed.

Now the version is the first eight characters of the file's SHA-256, and the stamping script walks every HTML file in the repository rather than a list:

JavaScript · scripts/stamp.mjs (excerpt)
const hashOf = file => createHash("sha256").update(readFileSync(file)).digest("hex").slice(0, 8);
const versions = { "site.css": hashOf("site.css"), "script.js": hashOf("script.js") };

for (const page of htmlFiles) {
  html = html.replace(/\/(site\.css|script\.js)\?v=[0-9a-f]+/g,
    (m, f) => "/" + f + "?v=" + versions[f]);
}

Unchanged file, unchanged URL, cache kept. Changed file, new URL, fetched once and cached again. The ?v= query string works with Cloudflare because the default cache key includes the query.

The purge you cannot skip

The two-hour HTML rule has a consequence that is easy to forget on the day you are in a hurry: after a push, the edge keeps serving the previous HTML until its two hours are up. The HTML is what references the new ?v=, so the new CSS is not even requested. The fix is one click — Caching → Configuration → Purge Everything — and it is the last thing the deploy script prints, in capital letters, with the link.

It is also the reason we keep two files around that no page references any more, for two hours after the change that made them orphans: a cached old page may still ask for them. Deleting an asset in the same commit as the pages that stop using it is how you get a broken icon on a legal page for an afternoon.

Could this be automated with the Cloudflare API? Yes, with an API token in the deploy script. We chose not to: the repository is public, the deploy script is in it, and a token that can purge (or worse) is not something we want one careless commit away from the internet. One click is cheap.

Headers that have to come from the edge

Because Pages sends no security headers, they are added with a Cloudflare response header transform rule: Strict-Transport-Security with preload, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, a Permissions-Policy that turns off camera, microphone, geolocation and payment, X-Frame-Options: DENY and Cross-Origin-Opener-Policy: same-origin. The Content-Security-Policy is the one exception — it travels with the HTML, as a meta tag, for reasons that note explains.

Verifying from the command line

Three headers tell you everything about a request's journey:

Shell
curl -sI https://duofine.com/ | grep -iE 'cf-cache-status|^age|cache-control'
  • cf-cache-status: HIT with a non-zero age means Cloudflare served it from the edge without asking the origin.
  • MISS or EXPIRED means it went to the origin this time; the next request should be a HIT.
  • cache-control is still the origin's max-age=600 — that is the browser TTL, untouched by the edge rule.

Run it after a deploy and a purge, and you have a one-line proof that the new version is live: the age resets to zero.

Setup cost: two rules and one transform rule, once. Running cost: one click per deploy. What you get: HTML from the edge everywhere, assets that never expire, and a stylesheet URL that only changes when the stylesheet does.
